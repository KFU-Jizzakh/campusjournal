# Use Cases (полный формат Алистера Кокбёрна)

Каждый кейс описан по fully-dressed шаблону. Исполняемым источником
истины остаётся тестовый набор (`tests/Feature/`); этот документ —
читаемая поведенческая спецификация системы.

## Акторы

| Актор | Описание |
|---|---|
| Автор | Податель рукописи или приписанный соавтор |
| Рецензент | Обладатель пермишена `review-article` |
| Секционный редактор | Ведёт workflow назначенных ему статей |
| Руководство | Главный редактор (EiC) или управляющий редактор (ME) |
| Админ | Системный администратор (Filament, полный доступ) |
| Контент-менеджер | Ведёт CMS-контент (Filament, ограниченный) |
| Анонимный читатель | Просматривает опубликованное без регистрации |
| Система | Планировщик, очередь, Crossref, почтовый реле |

---

### UC-1: Подать рукопись
**Цель:** автор регистрирует новую рукопись в системе.
**Область/уровень:** подача / пользовательский.
**Главный актор:** автор (пермишен `submit-article`, подтверждённый email).
**Второстепенные акторы:** соавторы, редакция.
**Заинтересованные стороны:** автор — трассируемость подачи; редакция — полные метаданные и контакты; система — корректный старт workflow.
**Предусловия:** аккаунт верифицирован; активная версия лицензионного договора существует (или договор отсутствует — тогда блок акцепта не рендерится).
**Гарантия успеха:** статья создана в статусе `submitted`; PDF на приватном диске; авторы и контакты заснапшочены на pivot; принятие договора зафиксировано (версия, пользователь, IP); запись `submission.created` в OutboxEvent; рубрика могла автоназначить секционного редактора; автор и соавторы уведомлены.
**Триггер:** автор отправляет форму подачи.
**Основной сценарий:**
1. Автор заполняет: название (≤500), аннотация RU (обязательно) и EN, рубрика, ключевые слова, PDF (≤50 МБ), свои контакты (email, телефон, страна, город — обязательны; сайт — опционален), соавторов, финансирование.
2. Система валидирует формат ORCID (`0000-0000-0000-0000`), уникальность ORCID внутри подачи, контакты соавторов.
3. Система создаёт статью и синхронизирует авторов: ORCID без привязки ищется/создаётся; строка, уже привязанная к чужому аккаунту, переиспользуется без изменений (контакты — в pivot-снапшот, профиль владельца не перезаписывается).
4. Система фиксирует акцепт договора и рассылает уведомления.
**Расширения:**
- 2a. ORCID привязан к другому аккаунту → ошибка валидации, подача не создаётся.
- 2b. У соавтора не заполнены контакты → ошибка валидации по конкретному полю.
- *c. Найдено похожее название (нормализованное совпадение, подстрока или similarity ≥88% среди поданных не-черновиков) → предупреждение со списком; статья не создаётся; загруженный PDF паркуется в сессии; подтверждающая повторная отправка не требует перевыгрузки файла; паркованный PDF переиспользуется только для того же названия; подача без PDF отвергается.
- 3a. Рубрика имеет маппинг на секционного редактора → тихое автоназначение, кроме случаев: маппинг на самого подателя, на пользователя без роли секционного редактора, на конфликтного редактора (автора статьи — по заявленной связи или pivot-email).
- *d. Финансирование: до 20 записей, `funder_name` обязателен, идентификатор — DOI/ISNI/ROR, хранится JSON-массивом на статье.
**Приоритет/частота:** критический / ежедневно.

### UC-2: Заявить соавторство по приглашению
**Цель:** соавтор привязывает перечисленную в рукописи запись автора к своему аккаунту.
**Область/уровень:** подача / пользовательский.
**Главный актор:** соавтор (зарегистрированный пользователь).
**Второстепенные акторы:** податель рукописи.
**Заинтересованные стороны:** соавтор — доступ к статье и уведомления; редакция — достоверный список авторов.
**Предусловия:** непривязанная строка автора содержит email, совпадающий с email аккаунта; подписанная ссылка приглашения отправлена (не чаще раза в 24 часа на строку).
**Гарантия успеха:** строка автора связана с пользователем; заявленный ранее ORCID «усыновлён» (unlinked-строка не дублируется).
**Триггер:** соавтор открывает подписанную ссылку из письма.
**Основной сценарий:**
1. Соавтор проходит по ссылке.
2. Система сверяет email pivot-снапшота с email аккаунта.
3. Система привязывает строку (при наличии ORCID — усыновляет существующую unlinked-запись, включая мягко удалённую).
**Расширения:**
- 2a. Податель вписал собственный email как соавтора → приглашение себе не отправляется (владельца доказать нельзя).
- 2b. ORCID записи привязан к другому аккаунту → заявка отклоняется.
- 2c. Срок подписи ссылки истёк → заявка отклоняется.
**Приоритет/частота:** средний / по мере приглашений.

### UC-3: Назначить секционного редактора
**Цель:** руководство закрепляет статью за секционным редактором.
**Область/уровень:** редакционный стол / пользовательский.
**Главный актор:** руководство (EiC/ME).
**Второстепенные акторы:** секционный редактор.
**Заинтересованные стороны:** редактор — понятная нагрузка; редакция — COI-безопасность; автор — движение подачи.
**Предусловия:** статья в статусе `submitted`; действующий пользователь — не автор статьи.
**Гарантия успеха:** `editor_id` установлен; событие `editor.assigned` в OutboxEvent; статья появилась в столе редактора.
**Триггер:** руководство назначает редактора (одиночно или bulk-операцией).
**Основной сценарий:**
1. Руководство открывает стол, выбирает редактора из списка с аннотацией нагрузки.
2. Система проверяет роль назначаемого (`section-editor`) и статус статьи.
3. Система фиксирует назначение.
**Расширения:**
- 2a. Назначаемый без роли секционного редактора → доменная ошибка, назначение не выполняется.
- 2b. Статья не в `submitted` → доменная ошибка.
- *c. Действующий — автор статьи (заявленная связь или pivot-email без claim) → 403; bulk-операция такие статьи пропускает поштучно (счётчик skipped), не прерывая остальные.
- *d. Секционный редактор не может назначать редакторов → 403 на уровне роута/полиси.
**Приоритет/частота:** высокий / ежедневно.

### UC-4: Пригласить рецензента
**Цель:** редактор назначает рецензента на статью.
**Область/уровень:** рецензирование / пользовательский.
**Главный актор:** секционный редактор (своя статья) или руководство.
**Второстепенные акторы:** рецензент.
**Заинтересованные стороны:** рецензент — ясные дедлайны; редакция — непротиворечивый пул; автор — двойное слепое не нарушено.
**Предусловия:** статья `submitted` или `in_review`; в double-blind загружен анонимизированный PDF; назначаемый имеет `review-article` и не является автором статьи.
**Гарантия успеха:** создана строка рецензии текущего раунда с дедлайнами (ответ 7 дней, рецензия 30 дней, настраивается); поставлено письмо в очередь (для double-blind — с инструкцией слепого рецензирования); первая назначка переводит статью в `in_review`.
**Триггер:** редактор выбирает рецензента в списке (отфильтрован по пермишену, с матчингом).
**Основной сценарий:**
1. Редактор выбирает рецензента.
2. Система создаёт рецензию и уведомляет редакцию.
**Расширения:**
- 2a. У рецензента уже есть активная (не declined/cancelled) рецензия в текущем раунде → блокировка на уровне приложения и частичным уникальным индексом.
- 2b. Рецензент завершал/отклонял рецензию в прошлом раунде → повторное приглашение разрешено, отправляется `ReviewReRequested`.
- 2c. В double-blind нет анонимизированного PDF → доменная ошибка, назначка не создаётся.
- 2d. Рецензент — автор статьи → COI-отказ.
**Приоритет/частота:** критический / ежедневно.

### UC-5: Ответить на приглашение
**Цель:** рецензент принимает или отклоняет приглашение.
**Область/уровень:** рецензирование / пользовательский.
**Главный актор:** рецензент.
**Второстепенные акторы:** редакция (уведомления).
**Предусловия:** рецензия в `pending`.
**Гарантия успеха:** статус `in_progress` (акцепт) либо `declined` (терминальный); редакция уведомлена in-app и по email.
**Триггер:** рецензент открывает страницу рецензии.
**Основной сценарий:**
1. Рецензент нажимает «Принять».
2. Система переводит `pending → in_progress`, уведомляет редактора (`ReviewerAccepted`).
**Расширения:**
- 1a. Рецензент отклоняет → `declined`, терминально; редактор может пригласить другого.
- 1b. Срок ответа (7 дней) истёк → напоминание планировщиком.
- *c. Админ может подменить рецензента (акцепт/отклонение за него) в рамках допустимых переходов.
**Приоритет/частота:** высокий / ежедневно.

### UC-6: Завершить рецензию
**Цель:** рецензент сдаёт заключение.
**Область/уровень:** рецензирование / пользовательский.
**Главный актор:** рецензент.
**Второстепенные акторы:** редакция, автор (получает анонимизированную обратную связь после решения).
**Предусловия:** рецензия `in_progress` (активное назначение даёт доступ к манускрипту, анонимизированному PDF и письму с ответом раунда).
**Гарантия успеха:** статус `completed` с рекомендацией (`accept`/`minor_revision`/`major_revision`/`reject`), комментарием редакции и комментарием автору; уведомления `ReviewCompleted` (редакция) и `AuthorReviewCompleted` (автор, критичное — без троттлинга); редактор может оценить качество (1–5).
**Триггер:** рецензент отправляет форму.
**Основной сценарий:**
1. Рецензент заполняет рекомендацию и оба комментария.
2. Система валидирует и переводит `in_progress → completed`.
3. Система уведомляет редакцию и автора.
**Расширения:**
- 2a. Незаполненные обязательные поля → ошибка валидации.
- 3a. Комментарии автора показываются автору только после решения редакции.
**Приоритет/частота:** высокий / несколько раз в неделю.

### UC-7: Отменить назначение рецензента
**Цель:** редакция снимает рецензента до завершения.
**Область/уровень:** рецензирование / пользовательский.
**Главный актор:** секционный редактор (свой статья) или руководство.
**Второстепенные акторы:** рецензент.
**Предусловия:** рецензия `pending` или `in_progress`.
**Гарантия успеха:** статус `cancelled` (терминальный); рецензент уведомлён (`ReviewCancelled`); guard дубликатов освобождён — рецензента можно назначить заново в том же раунде.
**Триггер:** редактор нажимает «Отменить назначение».
**Основной сценарий:**
1. Редактор подтверждает отмену.
2. Система переводит статус и уведомляет рецензента.
**Расширения:**
- 1a. Завершённая/отклонённая рецензия → переход запрещён стейт-машиной.
- 1b. Действующий — автор статьи → COI-отказ (403).
**Приоритет/частота:** средний / эпизодически.

### UC-8: Обсуждения в рамках workflow
**Цель:** участники переписываются внутри системы.
**Область/уровень:** коммуникации / пользовательский.
**Главный актор:** автор, рецензент, редакторы.
**Заинтересованные стороны:** автор — прямой канал с редакцией; редакция — внутренние обсуждения скрыты от автора; рецензент — приватная ветка со своим редактором.
**Предусловия:** статья в активном статусе (не черновик, не опубликована).
**Гарантия успеха:** сообщение сохранено со scope (`article`/`editorial`) и опциональной привязкой к рецензии; участники уведомлены (in-app + email, отключаемо в профиле).
**Триггер:** участник отправляет сообщение.
**Основной сценарий:**
1. Автор задаёт вопрос редактору (scope `article`).
2. Редактор отвечает в треде — ответ наследует scope и привязку родителя.
3. Система уведомляет участников треда, кроме автора сообщения.
**Расширения:**
- 1a. Редакция начинает редакционное обсуждение (scope `editorial`) или приватный тред с рецензентом (привязка к review) — автор их не видит.
- 1b. Рецензент пишет только внутри editorial-треда, привязанного к его собственной активной рецензии; declined/cancelled — только чтение; общий (`article`) scope рецензенту запрещён; привязка чужой/посторонней рецензии — 403.
- 3a. Тред закрыт (resolved) → ответы запрещены; закрыть/переоткрыть может только редактор; автор видит статус «закрыто».
- 3b. Сообщение >5000 символов или пустое → ошибка валидации.
**Приоритет/частота:** высокий / ежедневно.

### UC-9: Принять редакционное решение
**Цель:** редакция выносит вердикт по статье.
**Область/уровень:** редакционный стол / пользовательский.
**Главный актор:** секционный редактор (назначенная статья) или руководство.
**Второстепенные акторы:** автор.
**Заинтересованные стороны:** автор — мотивированное решение; редакция — целостность процесса; индексаторы — только опубликованное.
**Предусловия:** статья `in_review`; есть ≥1 завершённая рецензия **текущего** раунда; действующий не является автором статьи (COI: заявленная связь или pivot-email).
**Гарантия успеха:** статус `accepted`/`revision`/`rejected`; сохранены комментарий, `decided_at`/`decided_by`; отрендерено письмо решения; автор уведомлён (`AuthorDecisionMade`, критичное — без троттлинга); событие в OutboxEvent.
**Триггер:** редактор открывает форму решения.
**Основной сценарий:**
1. Редактор выбирает вердикт и пишет комментарий.
2. Система проверяет COI и наличие рецензий текущего раунда.
3. Система фиксирует переход и рендерит письмо.
4. Автор получает уведомление со ссылкой.
**Расширения:**
- 2a. Нет завершённых рецензий текущего раунда → доменная ошибка, статус не меняется.
- 2b. Действующий — автор статьи → 403 (read-only editorial-доступ сохраняется).
- 3a. Вердикт `revision` → статья в `revision`, автор видит комментарий и может править (UC-10).
- 3b. Вердикт `reject` → терминальный статус.
**Приоритет/частота:** высокий / несколько раз в неделю.

### UC-10: Доработать и подать повторно
**Цель:** автор возвращает переработанную статью.
**Область/уровень:** подача / пользовательский.
**Главный актор:** автор (податель).
**Предусловия:** статья `revision`.
**Гарантия успеха:** раунд инкрементирован (`current_round + 1`), статус `submitted`; письмо с ответом сохранено с новым раундом (в той же транзакции); анонимизированный PDF прошлого раунда удалён с диска и сброшены поля; поля решения/копирайтинга/продакшена очищены; секционный редактор сохранён; договор акцептован заново; редакция уведомлена (`AuthorResubmitted`).
**Триггер:** автор отправляет форму ревизии.
**Основной сценарий:**
1. Автор правит данные (при необходимости заменяет PDF — старый файл удаляется), заполняет письмо с ответом рецензентам (обязательно), опционально прикладывает файл (PDF/DOC/DOCX ≤50 МБ).
2. Система валидирует, включая повторный акцепт договора.
3. Система инкрементирует раунд и создаёт письмо с ответом.
**Расширения:**
- 2a. Пустое письмо с ответом или не принят договор → ошибка валидации, ревизия не принимается.
- 3a. Финансирование заменяется целиком.
- 3b. Соавторы синхронизируются: осиротевшие unlinked-строки удаляются, если не используются другими статьями.
**Приоритет/частота:** высокий / несколько раз в месяц.

### UC-11: Управлять доп. файлами
**Цель:** участники прикладывают к статье дополнительные материалы.
**Область/уровень:** файлы / пользовательский.
**Главный актор:** автор (статусы `draft`/`revision`) или редакция (любой не-черновик).
**Предусловия:** размер и тип файла прошли валидацию; выбраны тип, уровень доступа (`public`/`editorial_only`/`reviewers_only`) и лицензия.
**Гарантия успеха:** файл сохранён; для публичных изображений создана миниатюра 300×300; замена/удаление стирают старый файл с диска.
**Триггер:** участник загружает файл.
**Основной сценарий:**
1. Пользователь прикладывает файл и задаёт атрибуты.
2. Система сохраняет файл (и миниатюру).
**Расширения:**
- *a. Публичные файлы анонимно доступны только после публикации статьи.
- *b. `editorial_only` — только редакция; `reviewers_only` — редакция и назначенные рецензенты с активным назначением.
- *c. Автор может удалять свои файлы только в `draft`/`revision`; редакция — в любых не-черновиках (в рамках политики).
**Приоритет/частота:** средний / еженедельно.

### UC-12: Копирайтинг и продакшен
**Цель:** редакция готовит принятую статью к публикации.
**Область/уровень:** производство / пользовательский.
**Главный актор:** секционный редактор или руководство.
**Предусловия:** статья `accepted`.
**Гарантия успеха:** последовательность `accepted → copyediting → production` с фиксацией дат и исполнителей; откорректированный манускрипт (.docx/.pdf) загружен, предыдущая версия удалена с диска.
**Триггер:** редактор переводит этап или загружает файл.
**Основной сценарий:**
1. Редактор отправляет статью в копирайтинг.
2. Редакция загружает исправленный манускрипт (скачивание доступно редакции и подателю).
3. Редактор отправляет статью в продакшен.
**Расширения:**
- 3a. Попытка перевода в продакшен без загруженного файла → блокировка с сообщением об ошибке.
**Приоритет/частота:** средний / еженедельно.

### UC-13: Цикл утверждения гранок
**Цель:** автор подтверждает типографский PDF (galley).
**Область/уровень:** производство / пользовательский.
**Главный актор:** редактор загружает; автор утверждает.
**Предусловия:** статья `production`.
**Гарантия успеха:** гранка загружена; автор уведомлён (`AuthorGalleyReady`); утверждение переводит в `approved` и уведомляет редактора (`AuthorApprovedGalley`); каждый цикл правок журналируется (кто, комментарий, дата).
**Триггер:** редактор загружает galley-PDF и отправляет на утверждение.
**Основной сценарий:**
1. Редактор загружает гранку и отправляет автору.
2. Автор скачивает PDF и утверждает.
3. Система переводит `production → awaiting_approval → approved`.
**Расширения:**
- 2a. Автор запрашивает правки с комментарием → возврат в `production`, редактор уведомлён (`EditorGalleyRevisionRequested`); циклы не ограничены.
- *b. Публикация заблокирована до утверждения гранок автором.
**Приоритет/частота:** высокий / еженедельно.

### UC-14: Опубликовать статью
**Цель:** руководство публикует статью в выпуске.
**Область/уровень:** публикация / бизнес.
**Главный актор:** руководство с пермишеном `publish-issue`.
**Предусловия:** статья `approved`; выбранный выпуск `published`.
**Гарантия успеха:** статья `published` в выпуске, публично доступна; DOI засмичен (префикс + непрозрачный суффикс 8 символов из однозначного алфавита без `0/O/1/I/l`, без читаемых метаданных) и сохранён на статье; задепонирована фоновая задача Crossref (если включён и настроен префикс); счётчики просмотров/скачиваний активны.
**Триггер:** редактор выбирает выпуск и публикует.
**Основной сценарий:**
1. Редактор выбирает выпуск из списка опубликованных.
2. Система фиксирует публикацию и DOI.
3. Система ставит в очередь депозит Crossref (XML 5.3.1; результат — статус, HTTP-код, тело — в таблицу депозитов).
**Расширения:**
- 2a. Выпуск не `published` → инвариант нарушен, блокируется везде (модель, Filament, роуты, OAI, sitemap).
- 2b. У статьи уже есть DOI → новый не генерируется.
- 3a. Crossref выключен или префикс не настроен → депозит не ставится, `doi` остаётся пустым (backfill дороет позже).
- 3b. Ошибка депозита → до 3 повторов с бэкоффом 60/300/900 сек; DOI переиспользуется, не перегенерируется; каждая попытка — отдельная строка аудита.
- 3c. Ретракции/коррекции позже → ре-депозит с Crossmark-обновлениями (UC-16).
**Приоритет/частота:** критический / еженедельно.

### UC-15: Отозвать статью (withdraw)
**Цель:** снять статью из процесса до публикации.
**Область/уровень:** post-submission / пользовательский.
**Главный актор:** автор (свою, до публикации) или руководство (любую до публикации).
**Предусловия:** статья в не-терминальном, не-опубликованном статусе (переход разрешён стейт-машиной).
**Гарантия успеха:** статус `withdrawn` с причиной и датой; статья скрыта с публичного сайта (404), видна в editorial-столе и в списке подач автора; уведомления: редакторам — при инициативе автора (ME/EiC, если редактор не назначен), автору — при инициативе редакции (троттлинг 1 час); событие `article.withdrawn`.
**Триггер:** участник отправляет форму отзыва с причиной (обязательна, ≤5000).
**Основной сценарий:**
1. Пользователь указывает причину.
2. Система переводит статус и рассылает уведомления.
**Расширения:**
- 1a. Опубликованная/отозванная/отклонённая статья → доменная ошибка.
- 1b. Чужой автор без прав → 403.
**Приоритет/частота:** низкий / эпизодически.

### UC-16: Ретракшн и коррекции опубликованной статьи
**Цель:** исправить научную запись после публикации.
**Область/уровень:** post-publication / бизнес.
**Главный актор:** руководство (COI-гейт: автор статьи ретрактить не может; override админа сохраняется).
**Предусловия:** статья `published`.
**Гарантия успеха:** ретракшн — статус `retracted`, статья остаётся публичной с баннером и причиной; коррекции (corrigendum/erratum/expression_of_concern, опц. PDF-нотис, дата) видны на публичной странице и в редакционном интерфейсе; ре-депозит Crossref с `<update>`-элементами Crossmark; события `article.retracted`/`article.correction_added`; уведомления с троттлингом 1 час.
**Триггер:** руководство инициирует ретракшн/коррекцию.
**Основной сценарий:**
1. Руководство указывает причину ретракшна или данные коррекции.
2. Система фиксирует статус/записи и ставит ре-депозит.
3. Публичная страница показывает баннер/нотисы и кнопку Crossmark.
**Расширения:**
- 1a. Не-опубликованная статья → переход запрещён.
- 2a. Crossref включён, но Crossmark policy DOI не настроен → ре-депозит пропускается с предупреждением; пропущенные дорабатываются командой `crossref:redeposit` (`--dry-run`), без автоперезапуска.
- 2b. Удалены все коррекции → блок `<updates>` опускается; ретракшн-апдейт не вытесняет коррекции (ре-депозит заменяет запись целиком).
- 2c. Валидация Crossmark асинхронна: HTTP 2xx не гарантирует прохождение QC.
- 3a. Виджет Crossmark рендерится только при наличии DOI и настроенного policy DOI; невалидный policy DOI отключает виджет без падения (лог-раз в сутки).
**Приоритет/частота:** критический / редко.

### UC-17: Просмотр и обнаружение контента
**Цель:** читатель находит и потребляет опубликованное.
**Область/уровень:** публичный сайт / бизнес.
**Главный актор:** анонимный читатель.
**Второстепенные акторы:** OAI-харвестеры, Google Scholar.
**Гарантия успеха:** видны только опубликованные выпуски (`planned`/`in_progress` — 404 на всех публичных маршрутах, кроме них в sitemap и OAI) и опубликованные/ретрактнутые статьи; PDF, поиск (по названию/аннотациям/ключевым словам, только опубликованное, LIKE-экранирование), экспорт BibTeX (префикс ключа из настроек, `[A-Za-z0-9_-]`)/RIS/JATS; OAI-PMH: 6 глаголов, форматы oai_dc/oai_doaj/crossref, сеты по рубрикам и выпускам (кэш 5 мин), подписанные stateless resumption-токены с TTL, tombstone для мягко удалённых; sitemap только опубликованного; мета-теги citation_* для Scholar; счётчики просмотров/скачиваний дедуплицированы сессией (`?download=1` обязателен для скачивания).
**Триггер:** читатель открывает сайт/поиск/экспорт.
**Основной сценарий:**
1. Читатель открывает выпуск/статью или ищет.
2. Система отдаёт контент, при первом просмотре/скачивании за сессию инкрементит счётчики.
**Расширения:**
- 1a. Неопубликованный/не-существующий URL → 404.
- *b. Загруженный вручную JATS XML приоритетнее генерируемого; при невалидном XML — фолбэк на генерацию с записью в лог.
**Приоритет/частота:** критический / постоянно.

### UC-18: Администрирование системы
**Цель:** админ и контент-менеджер поддерживают справочники и настройки.
**Область/уровень:** админ-панель / системный.
**Главный актор:** админ; контент-менеджер (только группа «Контент»: события, страницы, конференции, организации).
**Гарантия успеха:** reference-data, пользователи/роли, выпуски, рубрики, авторы, рецензии, договоры, настройки поддерживаются через 12 Filament-ресурсов; журнал OutboxEvent и страница System Health (очередь, failed jobs, статус Crossref) доступны; контент-менеджеру остальное — 403 даже по прямому URL; EiC/ME в `/admin` не пускаются; смена статуса опубликованного выпуска блокируется при наличии опубликованных статей.

**Приоритет/частота:** средний / по мере необходимости.

### UC-19: Подтвердить email
**Цель:** пользователь подтверждает адрес.
**Область/уровень:** аккаунт / системный.
**Главный актор:** любой зарегистрированный пользователь.
**Гарантия успеха:** подписанная ссылка (60 минут, относительная подпись — работает за TLS-терминирующим прокси) подтверждает адрес; неверный хэш ничего не меняет; неподтвержденный пользователь удерживается на `/verify-email` для защищённых маршрутов; смена email в профиле сбрасывает подтверждение и рассылает новое письмо; повторная отправка — не чаще 6/мин.

**Расширения:**
- *a. Прод требует настроенного SMTP и работающего воркера очереди (`QUEUE_CONNECTION=database`); сидированные системные пользователи считаются подтверждёнными.
**Приоритет/частота:** критический / при каждой регистрации.

### UC-20: Контролировать нагрузку
**Цель:** каждый видит свои задачи.
**Область/уровень:** дашборд / пользовательский.
**Главный актор:** все роли дашборда.
**Гарантия успеха:** роль-зависимый инбокс: автор — черновики, ревизии, гранки на утверждение; рецензент — приглашения, незавершённые рецензии; редакция — следующее действие по статье (задача «Принять решение» появляется только при завершённой рецензии **текущего** раунда); ватчлист — «рецензирование идёт» (пока нет завершённой рецензии текущего раунда), ожидание гранок, доработка у автора; дедлайны рецензий (≤7 дней / просрочка); непрочитанные обсуждения; переключатель активной роли; статистика нагрузки.
**Триггер:** пользователь открывает `/dashboard`.
**Основной сценарий:**
1. Система определяет активную роль.
2. Система строит инбокс, ватчлист и дедлайны по workflow-состоянию (не по уведомлениям), сортируя по срочности.
**Расширения:**
- 1a. Пользователь с несколькими ролями переключает активную — наборы пересчитываются.
**Приоритет/частота:** высокий / постоянно.
